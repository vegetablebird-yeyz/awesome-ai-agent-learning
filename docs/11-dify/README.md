## 11.1 为什么我们还要学 Dify？

前两章我们一直在写代码：

- 用 LangChain 组装组件
- 用 LangGraph 编排流程

这条路线非常适合工程师，因为你能完全掌控系统细节。

但现实世界里，并不是每一个做 Agent 的人都想从零写框架代码。很多团队的真实诉求是：

- 先把产品原型快速搭出来
- 尽快验证业务价值
- 让产品经理、运营同学也能参与配置
- 把 Prompt、知识库、工作流集中管理

这就是 Dify 这类平台存在的原因。

### Dify 的一句话定义

> **Dify 是一个面向 LLM 应用与 Agent 的低代码开发平台。**

它帮你把很多工程工作变成了可视化配置，比如：

- 模型接入
- Prompt 管理
- 知识库接入
- Workflow 编排
- 对话历史管理
- 应用发布

### 什么时候该学 Dify？

如果你已经理解了前面的原理，现在去学 Dify 会非常舒服。因为你不会把它当成"神秘黑盒"，而是会把它理解成：

> 哦，这里是在配置 Prompt。  
> 哦，这里是在做工具调用。  
> 哦，这里其实就是一个图结构工作流。

## 11.2 Dify 的核心模块

很多人第一次打开 Dify，会觉得界面选项很多。其实你只要先抓住 4 个核心模块就够了。

| 模块 | 作用 | 对应我们前面学过的概念 |
|------|------|------|
| 应用（App） | 一个可发布的 AI 产品 | 你的 Agent 应用外壳 |
| Prompt / 对话编排 | 控制模型行为 | System Prompt / 行为规范 |
| 知识库（Knowledge） | 文档切分、检索、召回 | RAG |
| 工作流（Workflow） | 节点化流程编排 | LangGraph 式状态流 |

### Dify 不是只有聊天机器人

这是一个常见误解。

很多人以为 Dify 就是做一个问答窗口。其实它的覆盖范围比这个大得多：

- 聊天助手
- 知识库问答
- 表单驱动的内容生成
- 节点式自动化流程
- 多步骤业务助手

只不过它的交互入口通常都长得比较"像聊天"。

---

## 11.3 Dify 里最常见的两种应用形态

### 形态一：Chatflow / 对话型应用

这种最适合：

- 通用问答
- 知识库问答
- 简单工具调用
- 客服助手

特点是：

- 用户用对话方式输入
- 模型边理解边回答
- 很适合快速做 Demo

### 形态二：Workflow / 工作流应用

这种更适合：

- 报告生成
- 审批辅助
- 多步骤数据处理
- 需要明确节点控制的 Agent

特点是：

- 每一步流程都是显式的
- 更容易调试和复用
- 更适合复杂业务逻辑

### 一个非常实用的判断标准

如果你的需求是：

> 用户问一句，系统答一句

那优先考虑 Chatflow。

如果你的需求是：

> 先收集输入 → 再检索资料 → 再调用模型 → 再走审批 → 最后生成结果

那优先考虑 Workflow。

## 11.4 从零搭一个最简单的 Dify 应用

这一节我们不追求复杂，而是先建立最小闭环。

### 目标

搭一个"技术概念解释助手"：

- 用户输入一个概念
- 模型返回：
  - 一句话定义
  - 通俗类比
  - 常见误区

### 步骤1：创建应用

在 Dify 后台中：

1. 点击"创建应用"
2. 选择 `Chat Assistant` 或等价的对话型应用
3. 填写应用名称，例如：`AI 概念解释助手`

### 步骤2：配置模型

选择一个你已经接好的模型提供商，比如：

- OpenAI
- DeepSeek
- 通义千问
- Azure OpenAI

这一步本质上就是把我们前面写代码里的这几项，放到了页面上配置：

```python
model = ...
api_key = ...
base_url = ...
temperature = ...
```

### 步骤3：写系统提示词

你可以直接写成：

```text
你是一位耐心的 AI 老师。请用通俗、简洁的方式解释技术概念。

每次回答都包含三部分：
1. 一句话定义
2. 通俗类比
3. 常见误区

如果用户的问题太模糊，请先追问澄清，不要直接乱答。
```

### 步骤4：测试

输入：

```text
什么是向量数据库？
```

观察模型输出是否稳定、结构是否符合预期。

这就是一个最简单的 Dify 应用原型。

## 11.5 Dify 的真正价值：快

如果上面的应用让你手写，你当然也能写。

但你大概要做这些事：

1. 接一个前端页面
2. 接模型 SDK
3. 管理环境变量
4. 保存会话
5. 配置部署
6. 做基本调试

而在 Dify 里，这些基础设施你几乎都现成可用。

### Dify 最适合做什么？

我个人会把 Dify 的最佳使用场景总结成一句话：

> **Dify 特别适合"先把东西做出来"。**

比如：

- 两天内做一个客户演示原型
- 验证某个知识库问答场景有没有价值
- 让业务同学也能参与 Prompt 调整
- 把一个简单业务流程很快接入 LLM

它不一定永远是最终形态，但非常适合作为前期验证平台。

## 11.6 Dify 的知识库能力

这一块和我们后面的 RAG 章节关系非常紧密。

### 你在界面上看到的"知识库"，背后其实做了什么？

本质上还是那几件事：

1. 文档上传
2. 文本切分
3. 向量化
4. 存储到向量库
5. 用户提问时召回相关片段
6. 把片段塞回 Prompt

换句话说，Dify 只是把这些步骤产品化了。

### 这就是为什么我一直强调：先学原理，再学平台

如果你没学过 RAG，你会觉得：

> Dify 好神奇，上传文档就能问答。

但你学过之后会知道：

> 它做的其实还是切块、embedding、召回、拼接上下文这套流程。

知道原理的最大好处，不是让你更会背术语，而是当系统效果不好时，你知道该调哪里：

- 切块太大了吗？
- 检索结果不准吗？
- Prompt 没约束好吗？
- 引用片段不够吗？

## 11.7 Dify 的 Workflow：把业务流程可视化

这是 Dify 里我最建议你认真学的一部分。

因为当应用开始复杂时，单个聊天窗口已经不够表达你的业务流程了。

### 一个典型的工作流例子

比如做一个"周报生成助手"：

```text
输入本周工作内容
  ↓
提取关键事项
  ↓
按“完成事项 / 风险 / 下周计划”结构重写
  ↓
检查语气是否专业
  ↓
输出最终周报
```

在 Workflow 里，这些步骤可以显式画成节点。

### 可视化工作流有什么好处？

1. **流程更清楚**：不再把所有逻辑塞进一个超长 Prompt
2. **更好调试**：每个节点都能看输入输出
3. **更适合协作**：别人也能快速看懂你的系统结构
4. **更适合业务场景**：很多业务本来就是流程驱动的

你可以把它理解成"低代码版 LangGraph"。  
虽然底层灵活度不如纯代码高，但对很多业务团队来说已经足够好用了。

## 11.8 Dify 的边界在哪里？

学工具不能只看优点，不看边界。

### Dify 很强的地方

- 上手快
- 原型快
- 配置方便
- 知识库和对话能力开箱即用
- 适合跨角色协作

### Dify 的限制

#### 1. 深度定制能力有限

当你需要：

- 很复杂的工具执行逻辑
- 自定义路由策略
- 细粒度状态控制
- 很复杂的多 Agent 协作

这时纯代码通常会更合适。

#### 2. 抽象层带来的约束

平台型工具的本质是：  
它帮你省事的同时，也限制了你。

你能做的大多数事情，必须在它提供的表达方式里完成。

#### 3. 调到深处还是要懂原理

当效果不好时，如果只会点界面，不懂底层原理，你会很容易卡住。

比如知识库召回不好，到底是：

- 文档切分问题
- embedding 模型问题
- 查询改写问题
- rerank 问题

如果你不知道背后的机制，就只能反复试错。

## 11.9 那到底该选代码还是 Dify？

这是很多团队都会问的问题。

### 一个非常实用的判断表

| 场景 | 更推荐 Dify | 更推荐代码框架 |
|------|------|------|
| 快速做原型 | ✅ |  |
| 业务同学要参与配置 | ✅ |  |
| 只是做知识库问答 | ✅ |  |
| 流程相对固定 | ✅ |  |
| 需要复杂状态控制 |  | ✅ |
| 需要复杂工具编排 |  | ✅ |
| 需要多 Agent 深度协作 |  | ✅ |
| 需要高自由度定制 |  | ✅ |

### 我的真实建议

如果你是个人学习者：

- 想理解底层 → 先学代码
- 想快速做产品感 → 再学 Dify

如果你是团队：

- 先用 Dify 验证需求
- 验证通过后，再决定是否重构成代码系统

这是一条非常现实、非常常见的路径。

## 11.10 动手练习

### 练习1：做一个概念解释助手（难度：简单）

要求：

1. 创建一个对话型应用
2. 让输出固定包含三部分：
   - 一句话定义
   - 通俗类比
   - 常见误区
3. 测试至少 5 个技术概念

### 练习2：做一个周报生成工作流（难度：中等）

要求：

1. 设计 3-5 个节点
2. 支持输入本周事项
3. 输出结构化周报

建议节点：

- 信息提取
- 分类整理
- 语气润色
- 最终汇总

### 练习3：做一个知识库问答 Demo（难度：中等）

要求：

1. 上传一份你熟悉的文档
2. 建立知识库
3. 测试 10 个问题
4. 记录：
   - 哪些问题答得好
   - 哪些问题答得差
   - 你怀疑问题出在哪

这个练习非常重要，因为它会逼着你开始真正思考 RAG 效果。

## 11.11 小结

这一章的核心，不是教你点界面，而是帮你建立正确的认知：

| 知识点 | 核心内容 |
|------|------|
| Dify 的定位 | 面向 LLM 应用与 Agent 的低代码平台 |
| 对话型应用 | 适合快速做聊天助手和知识问答 |
| Workflow | 适合流程清晰的业务自动化 |
| 知识库 | 本质上还是 RAG，只是被产品化了 |
| 平台边界 | 快，但自由度低于纯代码 |

核心要点：

1. **Dify 的价值首先是快，其次才是低代码**
2. **它适合原型验证、业务协作、标准场景落地**
3. **当流程和逻辑足够复杂时，纯代码框架更灵活**
4. **懂原理的人用平台，会比只会点界面的人强很多**
